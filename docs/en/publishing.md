# Publishing a release (maintainers)

[English](publishing.md) · [Tiếng Việt](../vi/publishing.md)

A bm-render release is **nine npm packages with the same version**: `bm-render` (JavaScript, typings and
the wasm binaries) and eight platform packages `@hunghg255/bm-render-<platform>`, each holding one native Node-API
build. `bm-render` lists the eight as `optionalDependencies` pinned to its own exact version, so they must
all exist on the registry, at that version, before users install it. This page is the procedure; the
design is in [docs/NATIVE.md](../NATIVE.md), the user-facing behaviour in
[Getting started](getting-started.md#native-on-nodejs-webassembly-everywhere-else).

| Package | Built from | Contents |
|:--|:--|:--|
| `bm-render` | the repository root (`files` in `package.json`) | `js/`, the four `.wasm` files, READMEs, licenses; **no `.node` file** |
| `@hunghg255/bm-render-win32-x64-msvc`, `-win32-arm64-msvc`, `-linux-x64-gnu`, `-linux-x64-musl`, `-linux-arm64-gnu`, `-linux-arm64-musl`, `-darwin-x64`, `-darwin-arm64` | `npm/<platform>/`, generated by `npm run build:npm` | `bm-render.<platform>.node` (its `main`), `package.json` with `os` / `cpu` / `libc`, README, licenses |

`npm/<platform>/package.json` and `README.md` are committed; the `.node` files and license copies in
`npm/` are build output (git-ignored). The platform `package.json` files are generated from the root one
(version, license, author, repository, ...), so never edit them by hand.

## One-time setup

1. `author`, `homepage`, `repository` and `bugs` are set in the root `package.json` (hunghg255,
   https://github.com/BM-Hospital/bm-render). After changing any of them, run `npm run build:npm` to
   copy them into `npm/*/package.json`.
2. An npm account with two-factor authentication. The first `npm publish` of each name creates the
   package and makes you its owner; add co-maintainers to **all nine** with `npm owner add <user> <pkg>`.
   On 2026-11-12 none of the nine names existed on the registry (`npm view <name>` returned 404).
3. Zig 0.17.1 on `PATH` (or `ZIG=<path>`), and `npm install --ignore-scripts` in the repository root for
   `wasm-opt` (binaryen).

## Release procedure

**Short route: one command.** With the code committed:

```sh
npm run release:dry -- 0.1.1   # rehearsal: everything below with `npm publish --dry-run`, then reverted
npm run release -- 0.1.1       # the real release
```

`npm run release -- <version>` (scripts/publish.mjs) sets the version everywhere, rebuilds the wasm and its
manifest (`npm run build`), commits `Release <version>`, builds the native addon for the 8 targets and the
`npm/<platform>/` folders, runs every check (`npm run release:check`: verify, Zig tests, PDF tests, native
tests, pack test), publishes the 8 platform packages first and bm-render last, then tags `v<version>` and
pushes the commit and the tag. It refuses to start with uncommitted changes or without `npm login`. Packages
already published at that version are skipped, so an interrupted release (expired OTP, network) is finished
by running the same command again. Options: `--otp=<code>`, `--tag=<dist-tag>` (e.g. `next`),
`--skip-checks`, `--publish-only` (retry only the publishes after the checks passed on this commit). Without `--otp`, npm asks for a one-time password (or opens the browser) at each publish.
`prepublishOnly` runs the same checks, so a plain `npm publish` of bm-render cannot skip them. The steps
below are what the script does, one by one.

### 1. Set the version (one command)

```sh
npm run version:set -- 0.2.0
```

This rewrites, in one go: `version` in `package.json`, the eight `optionalDependencies` (exact `0.2.0`),
`package-lock.json` (root entry; stale `node_modules/bm-render-*` entries are dropped), and every
`npm/<platform>/package.json` + `README.md`. `npm run verify` fails whenever these disagree
(`node scripts/npm-platform-packages.mjs --check`). Do not use `npm version` alone: it would not touch
the optional dependencies or the platform packages.

### 2. Build everything

```sh
npm run build          # wasm: core, standard, full, woff + js/build-manifest.json (records the version)
npm run build:native   # 8 native targets -> native/dist/<platform>/, structurally verified, manifest.json
npm run build:npm      # npm/<platform>/: copies each .node (checked against native/dist/manifest.json)
```

`build:native` cross-compiles all eight targets from any one machine and fails on any structural problem
(see [NATIVE.md](../NATIVE.md#what-is-verified)). `build:npm` fails if a binary is missing, does not match
the manifest, or was not verified.

### 3. Verify

```sh
npm run verify                 # version sync + wasm manifest + no placeholders
npm run test:pack              # packs everything, installs it in scratch projects (~5 min)
npm run test:native            # the native test suite, on this machine's addon
node bench/native-identity.mjs # byte identity native vs wasm (needs bench/node_modules)
npm pack --dry-run             # main package file list: no .node, ~32 files, ~1.3 MB
for d in npm/*/; do npm pack --dry-run "$d"; done
```

`test:pack` runs the install scenarios with the real tarballs: the matching platform package selected by
npm, the wasm fallback without it (`--omit=optional`, missing, corrupted or foreign binaries),
`BM_RENDER_BACKEND`, `bm-render/native`, worker threads, bundlers. Locally only the host's binary can be
executed; the others are executed by the CI test matrix ([the CI route](#the-ci-route-manual-release-from-github-actions)). **Do not publish a platform that has never
passed `native-identity.mjs` and `native-tests.mjs` on its own OS and CPU** unless you accept that its users
may silently get wasm (the fallback) or, worse, a binary that loads but misbehaves.

### 4. Commit and tag

```sh
git commit -am "Release 0.2.0" && git tag v0.2.0
```

### 5. Publish: platform packages first, then bm-render

Order matters. If `bm-render@0.2.0` were published first, installs in the following minutes would skip
the not-yet-existing optional dependencies (silently: wasm), and lockfiles created then would not list them.

```sh
npm publish ./npm/win32-x64-msvc --access public
npm publish ./npm/win32-arm64-msvc --access public
npm publish ./npm/linux-x64-gnu --access public
npm publish ./npm/linux-x64-musl --access public
npm publish ./npm/linux-arm64-gnu --access public
npm publish ./npm/linux-arm64-musl --access public
npm publish ./npm/darwin-x64 --access public
npm publish ./npm/darwin-arm64 --access public
npm view @hunghg255/bm-render-darwin-arm64@0.2.0 version   # repeat for the others if in doubt
npm publish --access public                     # bm-render itself (prepublishOnly runs npm run release:check)
```

`--access public` is already in each `publishConfig`, it is repeated for clarity.

**2FA / OTP.** With "auth and writes" 2FA, every `npm publish` asks for a one-time password, or takes
`--otp=<code>`. A code is valid for about 30 seconds, so nine publishes need several codes; the CI route
below avoids this with a token.

**Provenance.** `npm publish --provenance` attaches a signed statement linking the tarball to the source
commit and the build. It only works from a supported CI provider (GitHub Actions with
`permissions: id-token: write`, GitLab), not from a laptop, and npm checks that `repository.url` in each
`package.json` is the repository the workflow runs in (another reason to fill in the placeholders).

### 6. Check the release

```sh
npm view bm-render@0.2.0 optionalDependencies
mkdir /tmp/check && cd /tmp/check && npm init -y && npm i bm-render@0.2.0
node --input-type=module -e 'const m = await import("bm-render"); console.log(m.backend)'   # native
```

## When something goes wrong

- **A platform publish fails** (network, OTP expired, name typo): nothing is broken yet, `bm-render` is not
  published. Fix the cause and publish the remaining platform packages; already-published ones answer
  `You cannot publish over the previously published versions` and can be skipped. Publish `bm-render`
  only when all eight exist.
- **`bm-render` is out, one platform package is missing**: users of that platform get wasm (the fallback),
  not an error. Publish the missing package with the **same** version as soon as possible; new installs
  pick it up. Lockfiles written in the meantime may lack it: those users need to reinstall.
- **A published platform binary is broken**: an npm version can never be overwritten, and unpublishing is
  only possible within 72 hours and blocks that version number forever. Deprecate instead:
  `npm deprecate @hunghg255/bm-render-<platform>@0.2.0 "broken, use 0.2.1"` (and `bm-render@0.2.0`), then release
  0.2.1 of **all nine** (versions move in lockstep; `version:set` does that). A user can force wasm in the
  meantime with `BM_RENDER_BACKEND=wasm`.
- **Mismatched versions** cannot happen through the scripts (`verify` checks), but if a platform package
  of another version is installed, its addon still loads only when its internal interface version (`abi`)
  equals the one `bm-render` expects; otherwise `bm-render` uses wasm.

## Prereleases and dist-tags

```sh
npm run version:set -- 0.3.0-beta.1
# build, verify, tag v0.3.0-beta.1 as above, then the same nine publishes with a tag:
npm publish ./npm/win32-x64-msvc --access public --tag next   # ... all eight
npm publish --access public --tag next
```

Always pass `--tag next` (or `beta`) for a prerelease, on all nine packages, so that `latest` keeps pointing
at the stable release; users opt in with `npm i bm-render@next`. The exact-version optional dependencies
make the tag of the platform packages irrelevant for resolution, but keep them consistent. To promote a
version later: `npm dist-tag add bm-render@0.3.0 latest` (and the same for the eight platform packages).

## The CI route: manual release from GitHub Actions

`.github/workflows/release.yml` releases without any npm login or OTP on your machine. Run it from
**Actions → release → Run workflow**:

| Input | Meaning |
|:--|:--|
| `version` | e.g. `0.1.1` or `0.2.0-beta.0`; empty = the version already in `package.json` |
| `dist_tag` | `auto` (`next` for prereleases, `latest` otherwise), `latest` or `next` |
| `dry_run` | build + test + `npm publish --dry-run`: nothing is committed, tagged or published |
| `skip_tests` | skip the per-platform tests, only to retry a publish whose tests already passed |

What it does: one Linux job bumps the version (when `version` differs), builds the wasm and cross-compiles
the eight addons with a pinned, checksum-verified Zig 0.17.1, and runs the Zig tests; eight test jobs
**execute** each addon on its own platform (Ubuntu x64 / arm64, Alpine x64 / arm64 in Docker, macOS x64 /
arm64, Windows x64 / arm64: `native-identity.mjs`, `native-tests.mjs`, the install scenarios); only when all
of that is green does the publish job commit `Release <version>`, push the `v<version>` tag, and publish
the eight `@hunghg255/bm-render-<platform>` packages and then `bm-render`, with provenance, skipping
versions already on the registry (so a failed run can simply be run again).

**One-time setup: npm trusted publishing.** On npmjs.com, for each of the nine packages (`bm-render` and the
eight `@hunghg255/bm-render-*`, once they exist on the registry): **Settings → Trusted Publisher → GitHub
Actions**, user/organization `BM-Hospital`, repository `bm-render`, workflow `release.yml`, environment
`npm`. npm then accepts publishes from this workflow through OIDC, with no token. (Alternative: a
repository secret `NPM_TOKEN` holding a granular token allowed to publish those packages; the workflow uses
it when it is set.) If `main` is a protected branch, allow GitHub Actions to push the release commit, or
bump the version locally and leave `version` empty.
