# Publishing a release (maintainers)

[English](publishing.md) · [Tiếng Việt](../vi/publishing.md)

A bm-engine release is **nine npm packages with the same version**: `bm-engine` (JavaScript, typings and
the wasm binaries) and eight platform packages `bm-engine-<platform>`, each holding one native Node-API
build. `bm-engine` lists the eight as `optionalDependencies` pinned to its own exact version, so they must
all exist on the registry, at that version, before users install it. This page is the procedure; the
design is in [docs/NATIVE.md](../NATIVE.md), the user-facing behaviour in
[Getting started](getting-started.md#native-on-nodejs-webassembly-everywhere-else).

| Package | Built from | Contents |
|:--|:--|:--|
| `bm-engine` | the repository root (`files` in `package.json`) | `js/`, the four `.wasm` files, READMEs, licenses; **no `.node` file** |
| `bm-engine-win32-x64-msvc`, `-win32-arm64-msvc`, `-linux-x64-gnu`, `-linux-x64-musl`, `-linux-arm64-gnu`, `-linux-arm64-musl`, `-darwin-x64`, `-darwin-arm64` | `npm/<platform>/`, generated by `npm run build:npm` | `bm-engine.<platform>.node` (its `main`), `package.json` with `os` / `cpu` / `libc`, README, licenses |

`npm/<platform>/package.json` and `README.md` are committed; the `.node` files and license copies in
`npm/` are build output (git-ignored). The platform `package.json` files are generated from the root one
(version, license, author, repository, ...), so never edit them by hand.

## One-time setup

1. Replace the `OWNER` / `AUTHOR_NAME` placeholders in the root `package.json` (`author`, `homepage`,
   `repository`, `bugs`), then run `npm run build:npm` to copy them into `npm/*/package.json`.
   `npm run verify` refuses to pass while placeholders remain.
2. An npm account with two-factor authentication. The first `npm publish` of each name creates the
   package and makes you its owner; add co-maintainers to **all nine** with `npm owner add <user> <pkg>`.
   On 2026-11-12 none of the nine names existed on the registry (`npm view <name>` returned 404).
3. Zig 0.17.1 on `PATH` (or `ZIG=<path>`), and `npm install --ignore-scripts` in the repository root for
   `wasm-opt` (binaryen).

## Release procedure

### 1. Set the version (one command)

```sh
npm run version:set -- 0.2.0
```

This rewrites, in one go: `version` in `package.json`, the eight `optionalDependencies` (exact `0.2.0`),
`package-lock.json` (root entry; stale `node_modules/bm-engine-*` entries are dropped), and every
`npm/<platform>/package.json` + `README.md`. `npm run verify` fails whenever these disagree
(`node scripts/npm-platform-packages.mjs --check`). Do not use `npm version` alone: it would not touch
the optional dependencies or the platform packages.

### 2. Build everything

```sh
npm run build          # wasm: core, standard, full, woff + js/build-manifest.json (records the version)
npm run build:native   # 8 native targets -> native/dist/<platform>/, structurally verified, manifest.json
npm run build:npm      # npm/<platform>/: copies each .node (checked against native/dist/manifest.json)
```

`build:native` cross-compiles all eight targets from any one machine and fails on any structural problem
(see [NATIVE.md](../NATIVE.md#what-is-verified)). `build:npm` fails if a binary is missing, does not match
the manifest, or was not verified.

### 3. Verify

```sh
npm run verify                 # version sync + wasm manifest + no placeholders
npm run test:pack              # packs everything, installs it in scratch projects (~5 min)
npm run test:native            # the native test suite, on this machine's addon
node bench/native-identity.mjs # byte identity native vs wasm (needs bench/node_modules)
npm pack --dry-run             # main package file list: no .node, ~32 files, ~1.3 MB
for d in npm/*/; do npm pack --dry-run "$d"; done
```

`test:pack` runs the install scenarios with the real tarballs: the matching platform package selected by
npm, the wasm fallback without it (`--omit=optional`, missing, corrupted or foreign binaries),
`BM_ENGINE_BACKEND`, `bm-engine/native`, worker threads, bundlers. Locally only the host's binary can be
executed; the others are executed by the CI test matrix ([the CI route](#the-ci-route)). **Do not publish a platform that has never
passed `native-identity.mjs` and `native-tests.mjs` on its own OS and CPU** unless you accept that its users
may silently get wasm (the fallback) or, worse, a binary that loads but misbehaves.

### 4. Commit and tag

```sh
git commit -am "Release 0.2.0" && git tag v0.2.0
```

### 5. Publish: platform packages first, then bm-engine

Order matters. If `bm-engine@0.2.0` were published first, installs in the following minutes would skip
the not-yet-existing optional dependencies (silently: wasm), and lockfiles created then would not list them.

```sh
npm publish ./npm/win32-x64-msvc --access public
npm publish ./npm/win32-arm64-msvc --access public
npm publish ./npm/linux-x64-gnu --access public
npm publish ./npm/linux-x64-musl --access public
npm publish ./npm/linux-arm64-gnu --access public
npm publish ./npm/linux-arm64-musl --access public
npm publish ./npm/darwin-x64 --access public
npm publish ./npm/darwin-arm64 --access public
npm view bm-engine-darwin-arm64@0.2.0 version   # repeat for the others if in doubt
npm publish --access public                     # bm-engine itself (prepublishOnly re-runs verify + test:pack)
```

`--access public` is already in each `publishConfig`, it is repeated for clarity.

**2FA / OTP.** With "auth and writes" 2FA, every `npm publish` asks for a one-time password, or takes
`--otp=<code>`. A code is valid for about 30 seconds, so nine publishes need several codes; the CI route
below avoids this with a token.

**Provenance.** `npm publish --provenance` attaches a signed statement linking the tarball to the source
commit and the build. It only works from a supported CI provider (GitHub Actions with
`permissions: id-token: write`, GitLab), not from a laptop, and npm checks that `repository.url` in each
`package.json` is the repository the workflow runs in (another reason to fill in the placeholders).

### 6. Check the release

```sh
npm view bm-engine@0.2.0 optionalDependencies
mkdir /tmp/check && cd /tmp/check && npm init -y && npm i bm-engine@0.2.0
node --input-type=module -e 'const m = await import("bm-engine"); console.log(m.backend)'   # native
```

## When something goes wrong

- **A platform publish fails** (network, OTP expired, name typo): nothing is broken yet, `bm-engine` is not
  published. Fix the cause and publish the remaining platform packages; already-published ones answer
  `You cannot publish over the previously published versions` and can be skipped. Publish `bm-engine`
  only when all eight exist.
- **`bm-engine` is out, one platform package is missing**: users of that platform get wasm (the fallback),
  not an error. Publish the missing package with the **same** version as soon as possible; new installs
  pick it up. Lockfiles written in the meantime may lack it: those users need to reinstall.
- **A published platform binary is broken**: an npm version can never be overwritten, and unpublishing is
  only possible within 72 hours and blocks that version number forever. Deprecate instead:
  `npm deprecate bm-engine-<platform>@0.2.0 "broken, use 0.2.1"` (and `bm-engine@0.2.0`), then release
  0.2.1 of **all nine** (versions move in lockstep; `version:set` does that). A user can force wasm in the
  meantime with `BM_ENGINE_BACKEND=wasm`.
- **Mismatched versions** cannot happen through the scripts (`verify` checks), but if a platform package
  of another version is installed, its addon still loads only when its internal interface version (`abi`)
  equals the one `bm-engine` expects; otherwise `bm-engine` uses wasm.

## Prereleases and dist-tags

```sh
npm run version:set -- 0.3.0-beta.1
# build, verify, tag v0.3.0-beta.1 as above, then the same nine publishes with a tag:
npm publish ./npm/win32-x64-msvc --access public --tag next   # ... all eight
npm publish --access public --tag next
```

Always pass `--tag next` (or `beta`) for a prerelease, on all nine packages, so that `latest` keeps pointing
at the stable release; users opt in with `npm i bm-engine@next`. The exact-version optional dependencies
make the tag of the platform packages irrelevant for resolution, but keep them consistent. To promote a
version later: `npm dist-tag add bm-engine@0.3.0 latest` (and the same for the eight platform packages).

## The CI route

`.github/workflows/release.yml` automates steps 2 to 5 on a `v*`
tag push: one Linux job builds the wasm and cross-compiles the eight addons with a pinned, checksum-verified
Zig 0.17.1; a test matrix **executes** every addon on its own platform (Ubuntu x64 and arm64, Alpine x64 and
arm64 in Docker, macOS x64 and arm64, Windows x64 and arm64) on Node 18, the current LTS and the newest
release (`native-identity.mjs`, `native-tests.mjs`, and the install scenarios once per platform); only when
all of that is green does the publish job release the eight platform packages and then `bm-engine`, with
`--provenance`, `--tag next` for prereleases, and skipping versions that are already on the registry (so a
failed run can simply be re-run). Requirements: the `NPM_TOKEN` repository secret (or npm trusted
publishing configured per package, after the first manual publish), the placeholders filled in, the action
SHAs and runner labels checked. `.github/workflows/ci.yml` builds and
tests on every push and pull request.
